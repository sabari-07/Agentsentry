## What went wrong

DynamoDB table `agentsentry-monitored` is rejecting writes because its provisioned write capacity is too low for the traffic it is receiving.

Read-only inspection of the live table shows it is on **PROVISIONED** billing with **1 WCU** and **1 RCU**. A single write consumes 1 WCU per KB, so 1 WCU sustains only about 1 small write per second. CloudWatch recorded **122 throttled `PutItem` requests in the last 15 minutes**, which means real client writes were refused with `ProvisionedThroughputExceededException` once the burst exceeded that ceiling.

This is a capacity-planning problem, not a code defect: the table's fixed capacity cannot absorb spiky traffic.

## Impact

- **Data loss risk:** every throttled `PutItem` is a write that did not land. Clients without retry logic silently lose that data.
- **User-visible errors:** throttling surfaces as 5xx/500 responses or failed operations in any service writing to this table.
- **Recurrence:** the same burst pattern will throttle again, because nothing about the table's capacity changes on its own.
- **Observed blast radius:** 122 rejected writes in a 15-minute window.

## The fix

Switching the table to **on-demand (`PAY_PER_REQUEST`)** billing removes the fixed ceiling entirely. DynamoDB then scales capacity automatically with traffic, so bursts are absorbed without anyone forecasting throughput. This is AWS's recommended mode for spiky or unpredictable workloads, and it eliminates the class of failure rather than just raising the limit.

```
Resources
[~] AWS::DynamoDB::Table MonitoredTable
 ├─ [-] BillingMode: PROVISIONED
 ├─ [-] ProvisionedThroughput: { ReadCapacityUnits: 1, WriteCapacityUnits: 1 }
 └─ [+] BillingMode: PAY_PER_REQUEST

# infra/agentsentry/stack.py
- billing_mode=dynamodb.BillingMode.PROVISIONED,
- read_capacity=1,
- write_capacity=1,
+ billing_mode=dynamodb.BillingMode.PAY_PER_REQUEST,
```

## Alternatives considered

| Option | Assessment |
| --- | --- |
| **On-demand billing** (chosen) | Removes the capacity ceiling permanently; no forecasting; scales with traffic. Best fit for bursty writes. |
| Raise provisioned WCU (e.g. 1 to 5) | Works only until traffic exceeds the new ceiling; still requires ongoing capacity planning. |
| Enable auto-scaling on provisioned capacity | Helps for gradual ramps, but reacts in minutes — too slow for sudden bursts like this one. |
| Client-side exponential backoff | Good defensive practice and complementary, but it hides the problem rather than fixing the capacity shortfall. |
